## Problem Statement

Brad, verbatim: "If I wanted to turn CCCFantasy.com into CCCFantasy an iOS (and maybe Android) application for as little $ as possible, how could I do it? Assume I know nothing about application stores and spaces. I do know we'd need a unique 'application not a website' feature(s), and I think push notifications to go along with our email system works."

Goal chosen: side project for the club (~50 members, entry fees not revenue). Delight per dollar.

## What Makes This Cool

- **The buzz on Saturday night.** "Ohio State won. You survive. So do 6 others. 3 fell. 31 remain." lands on the lock screen the hour the game goes final, riding the hourly game-day scores pass (ADR-063). Survivor grades straight-up (the spread is only the cumulative tiebreaker), so the verb is "won", never "covered". The Docket stamps each of your sides as it finals: "WIN: Huskers +3.5" / "7 sheets had them." (the verdict leads the title so a long team name truncates the number, never the verdict; 2026-09-25)
- **Three survivor verdicts, not two.** CFB Survivor has two lives, so a losing pick has two outcomes: "Ohio State lost. You lose a life. 1 left." or the elimination ceremony. In the tally, "fell" means lost a life or was eliminated on that game; "remain" is the pool's alive count after commit.
- **Elimination as ceremony.** A distinct push whenever `is_eliminated` flips, whether from a lost game or a DQ-2 no-pick at week completion: "Your run ends at Week 6. 19 remain." A DQ-2 life loss with no game attached pushes nothing (there is no verdict to report).
- **The nag with a red badge.** Survivor's day-before and final reminders — inclusive windows `[T-26h35m, T-24h25m]` and `[T-2h35m, T-25m]`, each firing hourly so a delivery missed to an outage gets a retry — and the Docket's 48h / 24h / 2h tiers arrive as a buzz too, and the icon badge shows what you owe until you open the app.
- **It's the room talking, not a receipt.** The email stays 1:1 and formal (the Club Letter); the push carries the club's tally, which the grading loop already knows because every pick on a game grades in the same run.

## Constraints

- **$0.** No Apple Developer Program ($99/yr), no Google Play ($25 + a 12-tester 14-day closed test), no vendor push service (Firebase, OneSignal).
- **No live scores.** ADR-063 deliberately declined the paid Odds API tier; nothing here adds an API call. Every push rides an existing timer.
- **Platform facts (verified against Apple's live docs 2026-09-14):** Web Push and the Badging API work for Home Screen web apps since iOS 16.4; the manifest must be `display: standalone`; permission must be requested from a user tap; the `Notification` API does not exist in a Safari tab on iOS, only in the installed app; there are no silent pushes on iOS (every push must show a notification or Safari revokes permission); the badge only changes when a visible push arrives or the app is open. Android Chrome supports all of it and offers its own install prompt.
- **Store review, if ever:** guideline 4.2's rejection text names "push notifications, Core Location, or sharing" as insufficient to elevate a wrapper beyond a repackaged website; a Capacitor shell loading a remote URL is the classic reject. Apple's own enrollment page: "If you build an app that you just want to show to family and friends, the App Store isn't the best way to do that."
- **Repo invariants that bind the build:** authenticated responses are `Cache-Control: private, no-store` (security invariant, `tests/test_response_cache_headers.py`); `/static/*` is served `immutable` for 30 days at nginx and every reference carries `?v=<sha>` (`tests/test_asset_versioning.py`); dependencies are exact `==` pins with transitives in `constraints.txt` (ADR-037/042); any env var read via `current_app.config` needs a matching line in `config.py`; every member email is a Club Letter (ADR-058); the reminder sent-flags are the only de-dup and there is deliberately no lock in code (PR #169).
- **Mid-season.** CFB Week 3 and Docket Week 3 are live. Nothing that sends today is refactored.

## Premises (agreed by Brad, D6; premise 2 re-confirmed after the cross-model challenge, D8; premise 5 corrected)

1. The "app" is cccfantasy.com made installable: web manifest + a root-served, push-only service worker + Web Push + the icon badge. $0, no store account, no review. iPhone (iOS 16.4+, after Add to Home Screen) and Android (Chrome install prompt).
2. Push is additive and rare: only two event families go out as push AND email, the deadline nag tiers and the your-game-went-final verdict (plus the elimination ceremony, which is a verdict). Picks-open, recaps, receipts stay email-only. A dead push token can never cost a member an email.
3. Subscriptions are per device, stored server-side against the user, keyed on the endpoint, upserted on every app open, pruned on 404/410, capped at 5 per user (insert past 5 evicts the oldest `last_seen_at`). Sending uses `pywebpush` with VAPID keys from `.env`, from the same systemd timers that send email today. Sending never raises into the caller.
4. The permission ask is a tap on a new `/app` page ("Turn on the buzz"). On iPhone the button exists only in standalone mode (iOS exposes the Notification API to Home Screen web apps only); in a Safari tab the page teaches the two-tap install instead. On Android the button is live in the browser tab too (Chrome exposes `PushManager` in-tab), so an Android member may subscribe without installing; installing is optional there and only needed for the icon badge. The gate is therefore feature detection (`'PushManager' in window && 'Notification' in window`), not a standalone check, and on iOS that resolves to standalone by itself. An installed iOS web app has its own cookie jar, so `/app` has a fourth state: standalone and logged out (login form, then return to `/app`). Members will log in once more inside the installed app. One Club Letter announces it.
5. The home-screen widget has no $0 version: Home Screen web apps have no widget API. It is reachable only through the store path, which is deferred until members ask, and would then need bundled assets and native features beyond push (4.2).
6. Doing nothing is fine: email already works. This is a delight feature for the club, not a fix.

Ruled out during the session:
- **App Store / Play Store wrapper now** (D3): $99/yr + review friction for a wrapper Apple's own rule rejects; the two chosen features work without it.
- **Push replaces email** (D4): a silently expired token would drop a member to zero reminders; the Saturday rescue nag must never depend on push.
- **Lock-screen Live Activity during your game** (D2): needs live scores every few minutes, the paid tier declined in ADR-063.

- **The 50% library:** `pywebpush` (+ `py-vapid`, `http-ece`, `cryptography`) does VAPID signing, payload encryption, the POST, `ttl`/`urgency`/`topic`, and surfaces 404/410 for pruning. Four new `==` pins + a constraints refresh.
- **Traps, all adopted as hard rules below:** SW at a root Flask route with `no-cache`, never under `/static/` (immutable at nginx, and scope would be `/static/js/`); NO `fetch` handler in the SW (a Cache API copy of `/docket/` on a shared phone is the cross-user leak the `no-store` invariant exists to prevent); gate the button on `matchMedia('(display-mode: standalone)')`; `requestPermission()` inside the tap handler; `pushsubscriptionchange` is unreliable, so upsert on open; VAPID private key is a secret to treat like `SECRET_KEY` (rotating it orphans every subscription); payload under 4 KB, `{title, body, url, tag, badge}` only; finals `ttl=6h, urgency=high`; nag `ttl=seconds_until_deadline, urgency=normal, topic=<game>-w<N>` so a late nag is dropped and the 2h nag replaces the 24h one; send AFTER commit, outside the game-day consumer's try/except (`games/gameday.py` rolls back and exits 1 on any error inside `apply`); Docket has no stored verdict, the transition is `is_final` flipping in `games/docket/services/scores.py::_apply_event`, grade the side there with `grading/engine.py::grade_pick_outcome`.

Evidence proposed: two weeks after the Club Letter, join `push_subscription.user_id` against the recipients of `run_reminder_check` / `run_reminder_pass`; if the overlap is under ~3 people, make the nag email-only and build the kickoff reveal instead. **Brad kept premise 2 (D8)**: the nag push is a few lines beside the existing tier send, the badge only exists via the nag push on iPhone, and the proposed join settles it with data instead of a guess.
- **Caveat for the Club Letter:** CFB's game-day `wants()` refuses games before the week deadline, so a Thursday survivor pick buzzes Saturday after 11:00 CT, not Thursday night. The Docket buzzes the night of.

## Approaches Considered

### Approach A: Push-only installable site (minimal)
Manifest, root push-only SW, subscribe button, subscription table, send helper, hooks at the two existing moments. Verdict copy is yours only. Effort M (human ~1 wk / CC ~1 day), risk low. Rejected as the cut because the verdict reads like a receipt; everything in A is inside C.

### Approach B: Shared outbox with per-member channel preference
Every game emits a notification event; one outbox routes email / push / both per a profile setting; absorbs the Aug 24 unified-email wedge; clean home for Golf in January. Effort L (human ~3 wks / CC ~2-3 days), risk medium. Deferred: it refactors the code that sends the Saturday rescue nag mid-season, and puts a preference column and profile UI ahead of the first buzz. Revisit in the December quiet window. (Amended 2026-09-21: the unified-email half was pulled forward into The Club Desk, ADR-065, `docs/designs/unified-email.md`; only the per-member channel preference stays in December.)

### Approach C: "The room talking" (chosen)
Approach A plus the social beat: verdict carries the tally, elimination gets its own push, Docket sides show how many sheets shared them. Kickoff reveal is the first follow-on. Effort M (human ~1.5 wks / CC ~1.5 days), risk low.

## Recommended Approach: C

Brad's goal is delight per dollar. The tally is the difference between a member reading the push and a member screenshotting it into the group chat, and it costs about half a day over A because the grading loop already sees every pick on a game in one run.

### Build shape (decision record, not a plan)

**New, platform-level (no game module imports; `tests/test_registry_seam.py` style):**
- `models/push.py::PushSubscription(id, user_id FK, endpoint String(512) unique, p256dh, auth, user_agent, created_at, last_seen_at)` + one Alembic migration (re-export in `models/__init__.py`). Insert past 5 per user evicts the oldest `last_seen_at`.
- `utils/push.py::send_push(user_ids, *, title, body, url, tag, ttl, urgency, topic=None, app_badge=None) -> int` (eng review 5A; design review renamed the count key): the helper builds the `{title, body, url, tag, app_badge}` payload from named fields (the key is `app_badge`, never `badge`, because `showNotification({badge})` is the Android status-bar glyph URL, which the worker hardcodes along with `icon`), so the games pass words and never JSON or library objects; it is the only module that imports pywebpush. Per subscription: a FRESH claims dict per call (pywebpush fills `aud`/`exp` in place, and a reused dict sends one push service's audience to another, which Apple rejects as BadJwtToken); `timeout=10`; `Urgency`/`Topic` go in the headers dict (Apple validates both strictly; Topic ≤ 32 URL-safe chars). On `WebPushException`: `status_code` 404/410 prunes the row; 429 logs with `retry_after` and skips this run (never retries in-loop); anything else logs. Log the user id, never the endpoint. Fan-out shape (eng review 10A): one `SELECT ... WHERE user_id IN (...)` for the subscriptions, one `requests.Session` per call passed to pywebpush for keep-alive to each push host, and a 120-second wall-clock budget per call; past the budget the remaining sends are skipped and the skipped count logged at WARNING, because every scores and reminder unit carries `TimeoutStartSec=5m` and a slow push service must end in a log line, not a SIGKILL mid-fan-out. Never raises, and "never raise" includes its own DB work: a failed prune write is rolled back inside the helper (`db.session.rollback()`), so the caller's next commit can never hit `PendingRollbackError`. Returns the delivered count. Blank VAPID config = no-op (mirrors the blank-`PAYMENT_*` convention). `utils.push` has no game import at all, top-level or lazy (eng review 1A: no cross-game badge count, no registry callable).
- VAPID public key reaches `push.js` through a `vapid_public_key` context-processor variable rendered as a `data-vapid-key` attribute on `<body>` in `base.html`.
- `core/push/` blueprint: `POST /push/subscribe`, `POST /push/unsubscribe` (JSON, login required, `X-CSRFToken`, rate-limited through the existing limiter). Subscribe validates the endpoint (eng review 2A): `https` only and the host must be on `PUSH_ENDPOINT_HOSTS` (`web.push.apple.com`, `fcm.googleapis.com`, `updates.push.services.mozilla.com`, `*.notify.windows.com`); anything else is a 400 logged at WARNING, so the droplet can never be made to POST into the private VPC or an arbitrary host. Subscribe is an ownership-following upsert (eng review 1A): the row for that endpoint is re-pointed to the current user (any row with the same endpoint under another user is deleted), because the browser returns the same endpoint for the installed app whoever is logged in, and a guest logging in after a GET logout must never inherit the previous member's verdicts. `/sw.js`, `/manifest.webmanifest` and the icons are anonymous-accessible (the manifest is fetched without credentials, and a login redirect there breaks Add to Home Screen); `GET /sw.js` (Flask route at the root; always sets `Cache-Control: no-cache, max-age=0` explicitly, eng review 4A, because Cloudflare caches `.js` by extension and the after_request hook only stamps logged-in responses; NO fetch listener; a `push` handler that ALWAYS calls `showNotification`, falling back to a fixed "Corrupt Commish Club: open the app" title/body when the payload fails to parse, since an undisplayed push costs the member their permission on iOS; and a `notificationclick` handler that focuses an open window at the payload `url` or opens one, eng review 3A), `GET /manifest.webmanifest` (`Cache-Control: max-age=300`; `name: "Corrupt Commish Club"`, `short_name: "CCC"`, `display: standalone`, `start_url: /`, `theme_color: #3A1D72`, `background_color: #140828` (Tribunal Black, so the launch screen matches the dark lounge instead of flashing white), icon URLs built with `?v={asset_version}` so `tests/test_asset_versioning.py`'s convention holds; icons: the existing 180, a 192 PNG (Android `icon`), and TWO 512s, `purpose: any` (the tile as-is) and `purpose: maskable` (the badger at 80% centered on a Council Purple field bleeding to every edge, because the tile's chin sits outside the maskable safe zone and Android's circle mask would crop it), plus a 96px white-on-transparent monochrome head-mark `badge` glyph for Android's status bar; all rastered locally from `static/img/logo/*.svg` by a `scripts/` one-off, since only the 180 exists today and iOS ignores SVG for Add to Home Screen; `base.html` also gets `<meta name="apple-mobile-web-app-title" content="CCC">` or the home-screen label becomes the page title truncated), `POST /push/test` (design review 4A: login + CSRF; sends the fixed "This is the buzz." payload to the posted endpoint only, through `utils/push.py::send_push_to_endpoint(user_id, endpoint, *, title, body, url, tag)`, which loads the one `PushSubscription` matching BOTH the endpoint and the current user (404 otherwise, so a member can never buzz another member's device) and shares the pywebpush send path with `send_push`; rate-limited 1/min per device with a route-level `key_func` of the sha256 of the posted endpoint, because `extensions.limiter` keys on `get_remote_address` and every phone on one household's Wi-Fi would otherwise share the quota; tested: same endpoint twice in a minute → 429, two endpoints from one IP → both 200), `GET /app` (the install/buzz page; eng review 7A: ONE template, the server decides only logged-in vs logged-out, and `push.js` decides the device facts after asking the device: `matchMedia('(display-mode: standalone)')` for installed, `pushManager.getSubscription()` for subscribed, `Notification.permission === 'denied'` for blocked, plus the old-iOS and Android-menu copy; the no-JS render always shows the install steps. The four visible states are Safari tab, standalone logged out, standalone unsubscribed, standalone subscribed). Logout: `/logout` is a plain GET link today, so `push.js` intercepts the logout click, calls `pushManager.getSubscription().unsubscribe()`, `POST /push/unsubscribe {endpoint}` (deletes only this device's row, other devices stay armed), then follows the link. A shared iPad therefore never buzzes the wrong person. If JS is off, the row survives and is pruned on its first 410 after the browser drops it; that is the accepted floor.
- `templates/base.html`: `<link rel="manifest">`, `apple-mobile-web-app-*` metas, one `static/js/push.js` (versioned like `countdown.js`) with the standalone gate, the upsert-on-open, and `clearAppBadge()` on open.
- `config.py`: `VAPID_PRIVATE_KEY`, `VAPID_PUBLIC_KEY`, `VAPID_SUBJECT` (`mailto:` + the commish mailbox), all via `os.environ.get`. `.env` on the droplet + `deploy/*.service` EnvironmentFile already load `.env`.
- Pins (ADR-037/042): `pywebpush==2.5.0` in `requirements.txt` (the current release on PyPI as of 2026-09-14; PR 1 re-checks and pins whatever is current then), plus `py-vapid==1.9.4` only if app code imports it for key generation (the plan generates keys locally, so it is expected to stay out of `requirements.txt`); `http-ece` (1.2.1 today), `cryptography` (50.0.1 today) and the rest land in `constraints.txt` via its header recipe. Watch the `py_vapid` deprecation warning under `cryptography` 46+ (class-vs-instance curve argument) before any constraints refresh.

**Hooks (each game owns its copy). The invariant is: push is called after the grading commit, and `send_push` never raises. The game-day wrapper's broad try/except (`games/gameday.py::run_game_day`) is therefore irrelevant to push; a push failure can never roll back a grade or fail the pass.**
- CFB: grading has three callers, and all three must push: `automation.py::run_scores` → `score_fetcher.py::ScoreFetcher.auto_process_week` → `game_logic.py::process_week_results` (the timer path), and the two admin correction routes in `games/cfb/routes.py` (`admin_mark_results` → `_apply_ruling` → `reverse_game_grade` → `process_week_results`). So the push lives in ONE helper, `games/cfb/services/reminders.py::push_survivor_verdicts(week, result)`, called after `process_week_results` returns (it commits at its end, after applying the DQ-2 no-pick life loss and the DQ-1 whole-pool revival) from `run_scores` and from both admin routes. `process_week_results` extends its summary dict with `graded: [(user_id, game_id, team, is_correct)]` and `eliminated_user_ids`. The latter is a this-run diff, not a state read: snapshot `is_eliminated` per enrollment before grading, and emit only users that flipped False→True in this run and are still eliminated after the DQ-1 revival and the commit. A Week 3 casualty is never re-buzzed in Week 4. The helper computes per game `survived`, `fell` (lost a life or eliminated on that game), `remaining` (pool alive count) and calls `send_push`. Tag `cfb-game-<id>`, `ttl=6h`, `urgency=high`, no `badge` key. Every user in `eliminated_user_ids` gets the ceremony under tag `cfb-elim-<week>`. An admin re-grade flows through the same helper and re-pushes the corrected verdict under the same tag, which replaces the earlier notification on the device.
- Docket: `is_final` flips one-way in `scores.py::_apply_event`; a post-final correction lands as `already_final` + `scores_written`, never as a flip. So `_apply_event` and `sync_scores` return `flipped ∪ {already-final games whose scores changed}` (today the summary only counts them). Because `_apply_event` overwrites `home_score`/`away_score` in place, it captures each affected side's outcome (via `sheets.py::_result`) BEFORE the assignment, but ONLY when `changed and game.is_final` (eng review 9A: the writer already computes `changed`; an unchanged final game does no grading reads, so the normal Sunday pass costs nothing extra), and returns the before/after pair; the caller compares after the commit. The three callers are exhaustive (no admin path writes `is_final`): `games/docket/services/gameday.py::apply`, and in `games/docket/cli.py` both the current-week `sync_scores` call and `_catch_up_previous_week` (a Monday-night final graded on Tuesday must buzz too). Each commits, then for every returned game reads each affected side's outcome through `sheets.py::_snapshot`/`_result` (the existing gated wrapper around `games/docket/services/grading/engine.py::grade_pick_outcome`; never a second rule, DESIGN.md §9), computes "N sheets had them", and calls `send_push`. Tag `docket-game-<id>`. For an already-final game, push only the sides whose captured before/after `_result` differs, so a cosmetic score edit never buzzes.
- Nag: `games/cfb/services/reminders.py::run_reminder_check` and `games/docket/services/reminders.py::run_reminder_pass` push the tier's recipient list regardless of the email outcome (a mail outage is exactly when push matters). Two different de-dups do two different jobs: `tag = <game>-w<N>-nag` replaces an already-delivered 24h notification with the 2h one on the device and keeps an hourly retry (the flag is not recorded when `sent == 0`) from stacking; `topic = <game>-w<N>` collapses messages still queued at the push service. `app_badge = 1` (eng review 1A: the badge means "you owe something", each game's nag pass sets it, the app clears it on open; no cross-game count), `ttl = seconds until deadline`, `urgency=normal`. No new timer. Copy grammar (layout pass 2026-09-25): iOS stacks title / "from CCC" / body and keeps the title to one line, so the title carries the message ("CFB pick due Sat 11 AM CT", "CFB pick locks in 1 hr 30 min", "Docket closes Sun 12 PM CT", "Docket closes in 2 hrs"; `utils/time.py::format_deadline_compact` / `format_time_left_compact`) and the body is one short line; budget 33 / 44 characters, locked in `tests/test_push_reminders.py`.
- Tally is garnish (eng review 6A): the post-commit reads that produce "31 remain" / "7 sheets had them" are wrapped in each game's hook; if either raises, the push still goes out with the tally-free body ("Ohio State won. You survive.") and the failure logs at WARNING. A verdict buzz never depends on a count.
- Copy: every push title/body is a Club Letter voice string beside its email twin, in `games/cfb/services/reminders.py` (CFB has no notifications module) and `games/docket/services/notifications.py`, under 40 / 120 chars.

**Rules (test-locked in `tests/test_push.py`, fourteen of them):** `/sw.js` has no `fetch` listener, has a `notificationclick` listener and a `showNotification` fallback branch, and answers with `Cache-Control: no-cache, max-age=0`; subscribe route requires login + CSRF; subscribe refuses an `http://` endpoint and a private-IP or unlisted host with 400; subscribe re-points an existing endpoint to the current user (subscribe as A, then as B with the same endpoint: only B's row remains); prune on 404/410; 429 is logged and skipped, never retried in-run; eviction past 5; `send_push` never raises and rolls back its own failed write; each call gets a fresh claims dict and a 10s timeout; a verdict for a game is pushed under one tag per game so a re-run replaces rather than stacks; the nag carries a tag; unsubscribe deletes only the posted endpoint; `build_home_context` and the lounge never import push or a game module, and `utils.push` imports no game module.

## Open Questions

- **Does the nag reach anyone who needs it?** (the cross-model challenge) Measure two weeks after the Club Letter: subscribers ∩ nag recipients. Under ~3 = nag goes email-only, effort moves to the kickoff reveal.
- **How many members are on iOS < 16.4?** Ask the group chat before the Club Letter; those members get "email still works" copy on `/app`.
- **Remember cookie in the standalone jar.** Both login paths use `login_user(remember=True)` and no `REMEMBER_COOKIE_DURATION` is set (Flask-Login default 365 days), so the 7-day session lapse should be bridged by the remember cookie. Confirm on a real iPhone that the remember cookie persists inside the installed app's separate jar; if it doesn't, the fourth `/app` state carries the load.
- **Android install (resolved 2026-09-14):** Chrome removed the service-worker-with-fetch-handler installability requirement in 2023 (developer.chrome.com/blog/update-install-criteria); a valid manifest is enough, the prompt itself is heuristic (visit frequency), and every Android user can install via the browser menu ("Add to Home screen" / "Install app") regardless. The `/app` page's Android copy points at the menu rather than promising an automatic prompt.
- **Docket per-side push volume:** up to 8 pushes per sheet per weekend. Acceptable for the club, or collapse Sunday-afternoon finals into one "3 more sides landed" push with a single tag? Decide after Week 1 of buzz.
- **Wireframe copy is stale on one word:** the sketch says "covered"; the doc's "won" is correct (straight-up grading).

## Success Criteria

- A member on iPhone completes Share → Add to Home Screen → Turn on the buzz in under a minute using only the `/app` page.
- The first Saturday: every survivor whose game finals receives one verdict push with the tally on the first game-day tick after the final (the pass wants a game 3-12h after kickoff, hourly :30 through game hours) or on the 08:00 daily pass overnight, matching the verdict shown on `/cfb/`; the same journal line shows the email still sent.
- Friday nag: subscribers among the no-pick list receive the buzz and the badge; no member receives a nag push after the deadline (TTL) or a stale tier (topic).
- Zero pushes fail the game-day pass: the journal shows grading committed before any push attempt; a push error is logged and the pass exits 0.
- A revoked/expired subscription is pruned on its first 410 and the member's email is unaffected.
- `ruff` clean, suite green, `tests/test_push.py` locks the fourteen rules above.
- Client code is smoked, not just source-asserted (eng review 8A): a `/browse` headless pass in PR 1 and PR 2 registers the worker, simulates a push with a good and a junk payload (DevTools push), asserts a notification shows both times and that click routes to the payload URL, and drives subscribe against a stub endpoint; one real-iPhone pass (install, permission, a hand-fired push, tap-to-open, logout intercept) happens before the Club Letter.

## Distribution Plan

The deliverable is the existing web service; `deploy.sh` covers it. Distribution to members is the Club Letter ("Put the Club on your home screen") linking `/app`, plus a small "Get the buzz" link on `/profile` and in the lounge (platform chrome, so PR 2 stays a single top-level `DESIGN.md` impeccable pass; room sub-navs are per-game chrome and stay untouched).
