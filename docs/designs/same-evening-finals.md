## Problem Statement

Brad, Saturday Sep 5 after the CFB deadline with several games finished: "no survivor lives were lost and no results were entered." Verified causes: `cfb-scores.timer` has no Saturday rule (Sun-Thu 08:00 CT) and the fetcher refuses pre-deadline anyway; the fetcher also graded nothing until every game settled (fixed by ADR-061). The Docket ledger shows a running record only when the daily 08:00 pass flips a game to `is_final`, so Thursday's result lands Friday morning and Saturday's on Sunday.

Brad's framing was "better live pulls within the free API tier" and "so much overlap in the API pull process that I am not using." The session reframed it: the ask is results the same evening, and the overlap is real but small.

## Facts established (re-verified, not the brief's guesses)

- Prod journal Sep 1-9: 55 of 500 credits used, pace about 185/month. Duplicated fetches (both games call `ncaaf/scores` on Sun/Mon/Tue; `cfb-spreads` and `docket-setup` both call `ncaaf/odds` Tuesday) about 20-35/month, about 6% of the tier.
- The Odds API docs: `/scores` without `daysFrom` costs 1 credit and returns "only live and upcoming games"; with `daysFrom` (1-3) costs 2. No period or clock in the response. The brief's option 1 (hourly 1-credit polls) would freeze a row on its last in-progress score after the final until the next morning; a pass that lands verdicts must pay 2.
- The Docket ledger already carries a mid-week record ("3-1 · 4 to play") from `is_final` games (`_live_week_board`, shipped #205). Nothing on either room reads an in-progress score. CFB grades per game (ADR-061) but the first post-deadline pass is Sunday 08:00.
- D5-eng (2026-08-11) ruled "share the client, not the fetch runs." This design reverses that for the game-day pass only.

## Premises (all four confirmed by Brad)

1. Members want their verdict and week record the same evening, not a running score mid-game.
2. The existing surfaces are right; only the cadence is wrong.
3. A shared `/scores` fetch fanned to both games is acceptable (reverses D5-eng).
4. In-game scores from The Odds API are not worth a column or a surface.

## Approaches Considered

- **A. Evening rules on the existing timers** (S): fixed slots, keeps every duplicate, hourly unaffordable. Rejected: pays every week in credits and misses odd-hour finals.
- **B. Shared game-day pass, self-limiting** (M): hourly timer, per-sport "could anything have ended?" guard, one fetch per sport fanned to both appliers, credit floor from the free `/sports` probe. **Chosen.**
- **C. Free scoreboard as trigger, Odds API to grade** (L): lowest credits, unofficial source with its own team names. Rejected while the tier has room.

## Recommended Approach

B. Implementation plan: `~/.claude/plans/review-docs-superpowers-specs-2026-09-07-spicy-widget.md`. Summary: `games/gameday.py` seam + `flask scores game-day --scheduled`; consumers in `games/cfb/services/gameday.py` and `games/docket/services/gameday.py`; one optional `events=` parameter threaded through each game's existing scores chain so grading, recap, open-retry and `is_final` semantics are untouched; `deploy/scores-gameday.{service,timer}` hourly at :30 (13:30-23:30 CT plus 00:30; December every two hours); `Persistent=false`; preset `ignore scores-*.timer`; ADR-063.

Estimated burn after shipping about 420/month at hourly cadence (baseline 185 + game-day about 235); the floor at 100 remaining protects the daily grading passes. The cadence step is the one knob; measure two weekends.
