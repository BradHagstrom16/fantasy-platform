| ADR-037 | Dependency version pinning | `>=` floors, `==` pins on direct deps, full lockfile | **`==` pins on direct deps** | ADR-031-era commit `308a0c4` (2026-04-23) converted every remaining `==` pin to a `>=` floor (`requests` was already a floor). A floor never pulls an environment forward, so each machine froze at whatever pip resolved on its install date and local/prod silently diverged across 16 packages — 13 of the 14 direct deps plus dev/transitive spill — with prod reaching gunicorn **26.0.0** (a 3-major jump) entirely unvetted. Exact pins make `pip install -r requirements.txt` converge the **direct** dependencies instead of leaving them wherever they landed. **This is deliberately not full environment reproducibility:** transitives (certifi, urllib3, idna, WTForms, alembic…) still resolve at install time and can differ between machines — prod already sits on WTForms 3.2.2 vs local 3.2.1. That is the accepted trade-off: floating transitives keep certifi/urllib3 patched without hand-maintaining ~40 lines. Transitive drift is *partially* caught — not prevented — by the pytest CI job added here (ADR-040 sibling) running the suite on every PR against a clean resolve. Two limits worth stating plainly: CI runs `ENVIRONMENT=testing` (in-memory SQLite), so a transitive regression that only manifests on Postgres passes green; and CI resolves transitives on the runner at PR time, not on the droplet at deploy time, so a green run proves the suite passed against *CI's* transitive set, not prod's. If a transitive ever needs holding, the mechanism is a pip **constraints file**, not a lockfile. **The cost of pinning, accepted knowingly: a pin freezes vulnerabilities too.** This PR demonstrated it immediately — pinning `click` at the 8.3.1 both machines happened to run froze a version inside PYSEC-2026-2132's affected range (command injection via `click.edit`), where the previous floor would have drifted onto a patched release by accident. Floors bought accidental patching at the cost of silent divergence; pins buy convergence at the cost of an explicit obligation to watch for advisories. `pip-audit -r requirements.txt` is the check, and it belongs in any future dependency-bump pass. | 2026-07-21 | Yes |

| ADR-040 | systemd unit propagation | Manual `sudo cp`, sync in deploy.sh | **Sync in `deploy.sh`** | Unit install was a manual `sudo cp` documented only in the unit's own header, so `deploy/*.service` edits never reached the server. Same failure shape as the dependency drift: a repo file treated as source of truth with no mechanism to propagate. Auto-propagation introduces its own risk — a semantically broken unit committed to the repo would previously have been inert and now deploys — so the sync is gated on `systemd-analyze verify` of the *repo* file before it lands (worst case: keep the known-good live unit, i.e. the pre-sync status quo), and the deploy verifies `systemctl is-active` after the restart. | ADR-041 | Units absent from `/etc` during the sync | Skip with notice, opt-in flag, repo manifest, **install unconditionally** | **Install every unit in `deploy/`** | ADR-040's sync covered one unit; the other 28 stayed in the silent-drift state it condemns. Generalizing it forced a policy call on the 20 units with no `/etc` counterpart (all `cfb-*`/`golf-*`). The backlog recommended skip-with-notice, reasoning that installing a unit for a service the box has never run is a different act from keeping an installed one current. Rejected: every alternative — a flag, a manifest, a runbook line — still requires a human at CFB launch week to remember a second step, which is the same shape as the `sudo cp` that left `--timeout 120` unshipped for five weeks. Installing is not enabling: systemd runs only what has been enabled or started, as the eight mothballed `worldcup-*` units sitting in `/etc` `disabled` demonstrate. Mirroring also makes the invariant checkable in one line (`deploy/` and `/etc/systemd/system/` agree), where skip-with-notice leaves a permanent expected mismatch, and it avoids printing "20 units skipped" on every deploy until Golf migrates (~Jan 2027) — warnings only work when they are rare. Accepted cost: `golf-*.timer` files now exist in `/etc` while Golf still runs on PythonAnywhere, so enabling them would double-run those syncs. Three mechanisms, established by checking the box after the first real deploy rather than by reasoning about it: the first guess was wrong outright, the second real but minor, and the one that matters was found only by reading `list-unit-files` afterwards. (a) `systemctl enable --now golf-*.timer` **cannot** do it: systemd rejects glob patterns for `enable`, and its globbing elsewhere matches only units already in memory, which a disabled timer is not. (b) Any form where the *shell* expands the glob — a loop over the files, or the glob typed from inside `/etc/systemd/system` — hands `systemctl` real paths and does work. (c) The real one: **`systemctl preset-all` would enable all fourteen timers**, with no glob involved and no game named — the four archived `worldcup-*` timers included, which predate this ADR and are the highest-consequence of the set (`worldcup-digest*` mails real players about a tournament that ended 2026-07-19). The droplet carries a single preset file (`90-systemd.preset`) with no catch-all rule, so unmatched units fall through to systemd's built-in *enable* default — `list-unit-files` confirms it, reporting every timer `disabled` with `PRESET enabled`. The ten `.service` units are immune (`static`, no `[Install]`). Left documented rather than machine-enforced by a preset file in this ADR's own PR; backlog 2.4 carries the case for building one, which the `worldcup-*` finding strengthened — that portion of the exposure has no expiry. Enable by explicit unit name; the deploy prints an explicit `NOT enabled` note on any first install. Orphan removal is deliberately out of scope (detecting "ours" needs game knowledge or persisted state, and deleting units is dangerous). Each unit gets an independent `systemd-analyze verify` verdict so one bad file warns without aborting the rest, and `daemon-reload` runs once after the loop. | 2026-07-21 | Yes |
| ADR-042 | Transitive dependency versions | Keep floating (ADR-037), eager-upgrade on every deploy, pin the security-relevant few, **pin all in a constraints file** | **Pin all transitives in `constraints.txt`** | Amends ADR-037, whose stated reason for letting transitives float — that floating "keeps certifi/urllib3 patched" — is false. `pip install -r requirements.txt` reports an already-satisfied transitive as satisfied and leaves it; even `--upgrade` only applies to packages *named* in the file, so only `--upgrade-strategy eager` moves them. Consequence, found 2026-07-21: prod had been on urllib3 2.6.3 across every deploy while 2.7.0 fixed CVE-2026-44431 (cross-origin redirect forwards sensitive headers) and CVE-2026-44432 (decompression beyond the requested amount), and on idna 3.13 against CVE-2026-45409 (quadratic-complexity DoS) — both runtime-reachable via `requests` in the CFB odds-API, Golf and WC sync paths. Practical risk was low (the urllib3 redirect bug needs the ProxyManager low-level API this code does not use; the idna bug needs attacker-controlled hostnames, and the app calls three fixed vendor APIs), but the mechanism was silent and unbounded. Rejected: eager-upgrade on every deploy, which lands unvetted versions in prod — precisely ADR-037's founding failure; and pinning only the security-relevant few, which leaves the rest drifting and does not deliver "everything current". Constraints were already ADR-037's named mechanism for holding a transitive, so this generalises it rather than inventing anything. `deploy.sh` and `.github/workflows/test.yml` both install with `-c constraints.txt`; the CI pip-cache key now includes it, since keying on `requirements*.txt` alone would reuse a cache built against the previous tree. Constraints are generated from **`requirements-dev.txt`**, not `requirements.txt` — CI installs the dev graph against this same file, so resolving from the prod graph alone would leave `pytest`'s own transitives (`pluggy`, `iniconfig`, `Pygments`) unpinned in the job that gates every PR; constraints for a package not being installed are ignored, so those entries cost the prod install nothing. `greenlet` is listed by hand — SQLAlchemy pulls it on Linux but not macOS, so a mac-generated freeze would leave the droplet unpinned. Cost accepted: refreshing is a manual, deliberate step. | 2026-07-21 | Yes |
| ADR-043 | Origin cloaking mechanism (backlog 2.6) | ufw CF-range allowlist on-droplet, nginx `allow`/`deny`, close port 80 entirely, **DO Cloud Firewall** | **DO Cloud Firewall `fantasy-platform-fw`: inbound TCP 22 from anywhere + 80/443 from Cloudflare's published ranges only; default allow-all outbound kept; ufw untouched** | Scanners were hitting the bare origin IP directly (access log, 2026-07-30), bypassing Cloudflare's WAF/DDoS layer (the ADR-031 architecture) — not a rate-limit gap after 2.5's realip fix, but the origin itself was fully exposed. The cloud firewall drops non-CF 80/443 at DO's network layer before the droplet, and is editable/detachable from the dashboard with **no SSH/sudo dependency** — sudo requires Brad's interactive TTY, so a firewall mistake must never be able to sever the only channel that can fix it. Detach restores service immediately because ufw underneath still allows 'Nginx Full' (additive layering: effective policy is the intersection; `ufw status` showing "Anywhere" forever is expected, not drift). Stateful, so allow-all outbound covers Managed Postgres :25060, Brevo :2525 and the vendor-API timers with zero inbound holes. No ACME casualty: the origin serves a 15-year Cloudflare Origin Certificate, so nothing renews over inbound :80. Rejected: ufw edit (an allowlist typo severs the SSH session used to fix it, and rules live only on the droplet — unauditable from the repo) and nginx `allow`/`deny` (origin stays reachable/fingerprintable at TCP/TLS; scanners still burn workers). | ADR-044 | `systemctl preset-all` enabling timers nobody chose (backlog 2.4, D13-eng) | Keep the prose "never run preset-all", `disable *` catch-all, WC-only rule, `disable` per game prefix, **`disable` the archived game + `ignore` the active ones** | **`deploy/10-fantasy-platform.preset` → `/etc/systemd/system-preset/`: `disable worldcup-*.timer`, `ignore` for `cfb-*`/`docket-*`/`golf-*`; own sync path + shape lint in `deploy.sh`** | ADR-041 named `preset-all` as the one mechanism that enables timers with no glob typed and no game named, and left it documented rather than enforced. Re-verified on the droplet 2026-08-13: 19 game timer unit files, **15 disabled with `PRESET enabled`** (not the 14 that ADR-041 and backlog 2.4 both quote — five `docket-*` landed in #142), box-wide 21. Unmatched units inherit systemd's built-in *enable* default, so preset-all would switch on all 15 — including four `worldcup-*` that mail real players about a tournament concluded 2026-07-19, all four with `Persistent=true`, so an accidental enable fires **immediately** rather than at the next tick. Prose in two docs was the only defence, which is precisely the remember-not-to-do-the-thing posture ADR-040/041 exist to replace. Three deviations from D13-eng as written, each forced by something checked on the box rather than reasoned about: (a) **filename keeps the `10-` prefix** — systemd.preset(5) sorts preset files lexicographically across all preset directories and takes the first matching line, so D13's bare `fantasy-platform.preset` would sort *after* the vendor `90-systemd.preset` (`'9' < 'f'`), harmless today only because that file happens to carry no matching rule; `tests/test_systemd_preset.py` locks the prefix below 90. (b) **Its own path in `deploy.sh`, not the unit loop** — `systemd-analyze verify` rejects a preset outright ("Invalid argument", exit 1), so D13's "unit sync extended to `*.preset`" cannot be implemented as written; validation is instead a bash shape lint requiring every pattern to clear three checks — a non-wildcard first character, a `.timer` suffix, and a prefix naming a game `deploy/` actually ships timers for. Each catches what the others let through, and a preset in `/etc` outranks the vendor policy for everything it matches: `disable *` is stopped only by the first, `disable getty@.service` only by the second, and `disable *.timer` (every timer on the box, `apt-daily` and `fstrim` included) only by the first; `disable apt-*.timer` clears both of those and is stopped only by the third. The prefix set is read from `deploy/*.timer` rather than hardcoded, so a new game needs no edit to the lint. (c) **`ignore` rather than `disable` for the three active games** — D13 was written 2026-08-11 when no docket timer was enabled; four are enabled now and five `cfb-*` follow at launch week, so a literal `disable docket-*.timer` would make preset-all silently stop in-season reminders. That trades one quiet footgun for another instead of removing it, and would need a deliberate flip at every future milestone. `ignore` leaves existing configuration intact in both directions, so preset-all becomes a true no-op for hand-managed families and this file never needs revisiting; `worldcup-*` stays `disable` because an archived game warrants an assertion, not a shrug. Also settles backlog 2.4's open judgement call on whether to list `cfb-*`/`golf-*` at all: listing them costs nothing under `ignore`. **World Cup unit files stay in `deploy/`** — removal was considered and rejected: ADR-041 puts orphan removal deliberately out of scope, so deleting them would strand all eight `/etc` copies (which is what preset policy actually reads) while destroying the revival recipe the transition plan preserves, reducing exposure by zero. Residual gap, accepted and made loud: a new game's prefix is uncovered until a line is added, so `tests/test_systemd_preset.py` fails CI on any `deploy/*.timer` prefix with no rule — the exposure went 4 → 14 → 19 by silent inheritance, and that is the loop this closes. **Postscript, 2026-08-13, learned the hard way:** the verification step originally written into this PR — `systemctl preset-all --dry-run` — **is not a dry run**. systemd accepts `--dry-run` and silently ignores it for `preset`/`preset-all` (only verbs like `reboot` honour it), and routes its output to stderr, so `> file` yields an empty file and the run reads as a no-op. Executed on the droplet minutes before the fix deployed, it enabled all 15 game timers for real plus `rsync`/`nftables`/`iscsid` and six system timers; recovered by `systemctl disable --now` naming each unit, with no timer having started and no mail sent. Two lasting consequences. First, the safe read is `systemctl list-unit-files 'worldcup-*.timer' 'cfb-*.timer' 'docket-*.timer' 'golf-*.timer' --no-pager` — no sudo, no writes, no pager — and it must be read in **both** columns, because they answer different questions and this incident is precisely where they disagree: `PRESET` is what policy *says* (`disabled` for `worldcup-*`, `ignored` for the active three) while `STATE` is what is actually enabled (`enabled` for `docket-{lines,scores,deadline,remind}` only; everything else `disabled`, `docket-setup.timer` included until after the Tue Sep 1 import by ruling).
