| ADR-037 | Dependency version pinning | `>=` floors, `==` pins on direct deps, full lockfile | **`==` pins on direct deps** | ADR-031-era commit `308a0c4` (2026-04-23) converted every remaining `==` pin to a `>=` floor (`requests` was already a floor). A floor never pulls an environment forward, so each machine froze at whatever pip resolved on its install date and local/prod silently diverged across 16 packages — 13 of the 14 direct deps plus dev/transitive spill — with prod reaching gunicorn **26.0.0** (a 3-major jump) entirely unvetted. Exact pins make `pip install -r requirements.txt` converge the **direct** dependencies instead of leaving them wherever they landed. **This is deliberately not full environment reproducibility:** transitives (certifi, urllib3, idna, WTForms, alembic…) still resolve at install time and can differ between machines — prod already sits on WTForms 3.2.2 vs local 3.2.1. That is the accepted trade-off: floating transitives keep certifi/urllib3 patched without hand-maintaining ~40 lines. Transitive drift is *partially* caught — not prevented — by the pytest CI job added here (ADR-040 sibling) running the suite on every PR against a clean resolve. Two limits worth stating plainly: CI runs `ENVIRONMENT=testing` (in-memory SQLite), so a transitive regression that only manifests on Postgres passes green; and CI resolves transitives on the runner at PR time, not on the droplet at deploy time, so a green run proves the suite passed against *CI's* transitive set, not prod's. If a transitive ever needs holding, the mechanism is a pip **constraints file**, not a lockfile. **The cost of pinning, accepted knowingly: a pin freezes vulnerabilities too.** This PR demonstrated it immediately — pinning `click` at the 8.3.1 both machines happened to run froze a version inside PYSEC-2026-2132's affected range (command injection via `click.edit`), where the previous floor would have drifted onto a patched release by accident. Floors bought accidental patching at the cost of silent divergence; pins buy convergence at the cost of an explicit obligation to watch for advisories. `pip-audit -r requirements.txt` is the check, and it belongs in any future dependency-bump pass. | 2026-07-21 | Yes |
| ADR-038 | gunicorn 23 → 26 | Hold at 23, adopt 26 | **Adopt 26.0.0** | Already running in prod via the floor. Remainder is RFC 9112/9110 parser hardening, which sits behind nginx + Cloudflare. Added `--no-control-socket`: ≥25.1 opens a `reload`/`shutdown`-capable control socket by default and nothing here uses `gunicornc`. | 2026-07-21 | Yes |
| ADR-039 | Deps held back deliberately | Take latest everything, hold specific majors | **Hold Werkzeug 3.2, SQLAlchemy 2.1, Flask-SQLAlchemy 4** | Werkzeug **3.2.0** changes `redirect()` from 302 to **303** and removes `OrderedMultiDict` — pinned at 3.1.8 so it can't arrive unannounced. SQLAlchemy 2.1 is beta only (2.1.0b3). Flask-SQLAlchemy **4.0** removes `Model.query`, used on **495 lines across 64 files** repo-wide (356 lines / 35 files of app code, the rest in `tests/` — which must migrate too) — that migration is its own project. `pytz` dropped entirely: zero imports repo-wide, fully superseded by `zoneinfo`. | 2026-07-21 | Yes |
| ADR-040 | systemd unit propagation | Manual `sudo cp`, sync in deploy.sh | **Sync in `deploy.sh`** | Unit install was a manual `sudo cp` documented only in the unit's own header, so `deploy/*.service` edits never reached the server. Discovered during the ADR-037 audit: the `--timeout 120` fix committed 2026-06-11 (`ad44a8b`) was still not live on 2026-07-21, leaving prod on gunicorn's 30s default — which would SIGKILL a worker mid-announce (synchronous SMTP, one connection per recipient). Same failure shape as the dependency drift: a repo file treated as source of truth with no mechanism to propagate. Auto-propagation introduces its own risk — a semantically broken unit committed to the repo would previously have been inert and now deploys — so the sync is gated on `systemd-analyze verify` of the *repo* file before it lands (worst case: keep the known-good live unit, i.e. the pre-sync status quo), and the deploy verifies `systemctl is-active` after the restart. The latter matters independently of this change: the unit is `Type=simple`, so `systemctl restart` returns 0 as soon as the fork succeeds, whether or not gunicorn survives. `deploy.sh` now also exits non-zero when any non-fatal step warned, so a partially-synced deploy cannot end on "App is live". | 2026-07-21 | Yes |

## Notes

- **Reversibility column** — "Yes" means changeable without migration; "Hard" means schema/code rewrite; "No" means baked into history.
- **Supersession** — when an ADR is overruled by a later one, both are kept (the older is annotated, the newer references it). The history of the decision matters as much as the current state.
- **Current conventions live in [CLAUDE.md](CLAUDE.md)** — this log is the *why* of past choices, not the *how* of current code.
