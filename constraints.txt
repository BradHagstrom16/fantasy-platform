# Transitive dependency pins (pip constraints file).
#
# WHY THIS EXISTS (ADR-042, amending ADR-037). ADR-037 left transitives floating on
# the stated grounds that floating "keeps certifi/urllib3 patched". That is not what
# pip does: `pip install -r requirements.txt` — even with --upgrade — reports an
# already-satisfied transitive as satisfied and leaves it alone. Prod therefore sat on
# urllib3 2.6.3 across every deploy while 2.7.0 fixed CVE-2026-44431 and CVE-2026-44432,
# and on idna 3.11/3.13 against CVE-2026-45409. Floating gets you current on a FRESH
# install, never on an existing one.
#
# SCOPE: this covers BOTH graphs — what requirements.txt pulls in (prod, via deploy.sh)
# and what requirements-dev.txt additionally pulls in (CI, which installs the dev graph
# with this same -c file). Generating from requirements.txt alone would leave pytest's
# own dependencies unconstrained in the job that gates every PR. Constraints for a
# package that is not being installed are ignored, so the dev entries cost prod nothing.
#
# Direct dependencies are pinned in requirements.txt / requirements-dev.txt and MUST NOT
# be repeated here — one pin per package, one place. This file covers only what those
# pull in.
#
# HOW TO REFRESH (deliberate, never automatic — that is the whole point):
#   python3 -m venv /tmp/resolve && /tmp/resolve/bin/pip install --upgrade pip
#   /tmp/resolve/bin/pip install --upgrade --upgrade-strategy eager -r requirements-dev.txt
#   /tmp/resolve/bin/pip freeze   # drop names pinned in requirements*.txt, keep the rest
#   # then: run the suite, run pip-audit, deploy, verify on the droplet.
# Resolve from requirements-dev.txt, NOT requirements.txt — it is `-r requirements.txt`
# plus tooling, so it yields the superset. --upgrade-strategy eager is load-bearing;
# without it nothing here moves.
#
# greenlet is listed by hand: SQLAlchemy pulls it on Linux but not macOS, so a
# mac-generated freeze omits it and the droplet would be left unpinned.
#
# THIS FILE PINS, IT DOES NOT PRUNE. pip never uninstalls: a package dropped from
# requirements.txt stays installed on every environment that already had it, forever,
# and neither `-r` nor `-c` will remove it. So "installed" can exceed "declared" and
# nothing reports the difference.
#   Worked example: pytz was a direct dependency (`pytz>=2026.1.post1`) from Phase 0
#   until commit 1ff0a1f dropped it on 2026-07-21. Prod still carried pytz==2026.2
#   afterwards — orphaned, nothing importing it, `pip show` reporting an empty
#   Required-by, and the repo using zoneinfo by convention anyway.
# Removing an orphan is a manual, per-environment act. Verify first, then:
#   venv/bin/pip show <pkg>          # Required-by MUST be empty
#   venv/bin/pip uninstall -y <pkg>
# To find them: compare `pip freeze` against requirements*.txt + this file.
